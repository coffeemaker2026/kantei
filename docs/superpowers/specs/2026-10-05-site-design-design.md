## 1. 目的と前提

### ねらい
基本機能（鑑定してカードにする）とサイトデザインを、公開できる水準に近づける。今回は改善候補 C・B・A のうち **C（サイトデザイン）** を扱う。B（カードのデザイン）と A（言葉の部品を増やす）は、この設計が終わったあとに別の設計書で扱う。

### 今の試作の課題（2026年10月5日にスクリーンショットで確認）
- 見た目が入力フォームのままで、「鑑定所」に来た感じが薄い。サイト名を出す場所がない
- スマホでは最初の画面がカードの裏面で埋まり、何をするサイトかがスクロールしないとわからない
- 鑑定の流れに見せ場がない（ボタンを押すとすぐカードがめくれて終わる）
- ブラウザ標準の英語の部品（「Choose File」）がそのまま見えている

### 守る方針（CLAUDE.md より）
- サイトの動作中に AI もサーバーも使わない。S3 の静的サイトとして動く
- 写真は外に送らない・保存しない
- 「カードダス」の名前やデザインを使わない
- 実在の宗教を茶化さない。笑いの対象は「お役所仕事」にし、神社・寺院の見た目には寄せない

## 4. ファイル構成

```
/workspace
  package.json            Vite・Vitest・Playwright を開発用として入れる
  vite.config.js          root を frontend/ にし、4ページを入口として登録する
  playwright.config.js
  tests/                  画面のテスト（Playwright）
  frontend/
    index.html            手続きの画面（①〜④）
    about.html            鑑定所について
    privacy.html          プライバシーポリシー・免責事項
    contact.html          お問い合わせ
    src/
      css/site.css        4ページ共通（色・書体・ヘッダー・フッター・申請書の部品）
      css/kantei.css      手続きの画面だけで使うもの
      js/main.js          画面の切り替え（①〜④）、入力・ボタンの操作、エラーの表示
      js/appraise.js      判定（乱数・ランク・ステータス・伝承文）。DOM に触れない
      js/appraise.test.js 判定のテスト（Vitest）
      js/signature.js     写真の署名（8×8・明るさ8段階）
      js/card.js          カードの描画（750×1050 の Canvas）
      js/editor.js        写真の調整（位置・大きさ・なぞって切り抜く）
      js/samples.js       見本の写真（Canvas で描く）
    public/               そのまま公開するもの（ファビコンなど）
    dist/                 npm run build の出力。S3 に上げるのはここ（Git の管理外）
```

- `frontend/shinki-kantei.html` は削除し、`index.html` に置き換える
- 各モジュールの役割：
  - `appraise.js`：入力（名前・写真の署名・種類・再審回数）から判定結果のオブジェクトを返すだけ。Canvas や DOM に依存しないので、Node 上でテストできる
  - `card.js`：判定結果と写真の調整状態を受け取り、Canvas を返す
  - `editor.js`：写真の調整欄の操作と状態（位置・大きさ・切り抜きの座標）を持ち、`card.js` に渡す
  - `main.js`：上の部品をつなぎ、画面の切り替えを担う

## 5. 開発環境と配信

- 開発中：`npm run dev` で Vite の開発サーバー（5173番）を立てる。devcontainer の `forwardPorts` に 5173 を足して自動で転送する。コンテナの外から開けるよう、Vite は `0.0.0.0` で待ち受ける
- 本番に近い確認：`npm run build` で `frontend/dist/` を作り、nginx で配信して見る
  - `compose.yml`（8080番）と devcontainer の `web` の両方で、マウント元を `frontend/` から `frontend/dist/` に変える
  - nginx の `index` を `shinki-kantei.html` から `index.html` に変える
  - `Dockerfile` の `COPY` も `frontend/dist/` に変える
- `post-create.sh`：今の `npm ci` と Chromium のインストールに加え、`npm run build` を行う（`web` コンテナが最初から何かを配信できるようにするため）
- `frontend/dist/` は `.gitignore` にだけ足す（`Dockerfile` が `dist/` をコピーするので、`.dockerignore` には足さない）
- `package.json` のスクリプト：`dev`・`build`・`preview`・`test`（Vitest）・`test:e2e`（Playwright）

## 6. 画面の設計

### 共通
- ヘッダー：「八百万神器鑑定所」（明朝・金）、右側に札（①では「鑑定所について」へのリンク、②〜④では「受付番号 0427」）
- 手続きの表示：①受付・②申請・③審査・④交付。今いる画面は金、終わった画面は薄い色
- フッター：3ページへのリンク
- 4つの画面はすべて `index.html` の中にあり、JS で切り替える。`history.pushState` を使い、ブラウザの「戻る」で1つ前の画面に戻れるようにする
- 写真は保存しないので、③・④で再読み込みしたときや、写真がない状態で②より先に進もうとしたときは②に戻す
- ①〜③はパソコン幅でも中央の1列（幅 640px 程度）。④だけ2列（左にカード、右にボタンと説明）

### ① 受付
- 見出し「その持ち物、神器かもしれない。」と、短い説明（「写真と名前を申請すると、神々が審査して鑑定カードを交付します。」）
- 見本のカード3枚を扇形に並べる。画像は見本の写真から、ページを開いたときに `card.js` で描く（画像ファイルを持たない）
- 朱色のボタン「番号札を取る」。押すと受付番号を決めて②へ進む
  - 受付番号は4桁。ページを開いた時刻から作る見た目だけの番号で、判定には使わない
- 黄色い注意書き「※ 写真はこの端末の中で使うだけで、どこにも送りません」
- 広告枠（ボタンより下）

### ② 申請
- 生成りの紙に二重線の枠で「神器鑑定申請書」、その下に「様式第8号（第3条関係）」、右上に朱の「受付」の判子
- 太枠の記入欄：品名（16文字まで）・分類（今の7種類）・現物写真
- 現物写真：ブラウザ標準のファイル選択は見えないようにし、自前の「写真を添付する」ボタンで開く。貼り付け・ドラッグ＆ドロップも今どおり受け付ける
- 写真を添付すると、同じ申請書の中に「添付写真の調整」欄を開く（位置を動かす・なぞって切り抜く・大きさ。今の機能のまま）
- 黄色い注意書き「※ 太枠内をご記入ください」
- 朱色のボタン「申請する」で③へ
- 申請書の下に小さく「写真がないときは 見本で試す」。押すと見本の写真3種類を選べる（本番で残すかは D で決める）

### ③ 審査
- 電光掲示板風の枠に「ただいま審査中の番号」と受付番号（オレンジに光る等幅の数字）
- 文言を約1秒ずつ3つ流す（例：「神々が協議しています」「前例を確認しています…」「担当の神が席を外しています…」）。文言は配列で持ち、A で増やせるようにする
- 黄色い注意書き「※ 審査の順番に関するお問い合わせにはお答えできません」
- 「タップで飛ばせます」。画面のどこかをタップするか、キーを押すと④へ
- 再審のときは「再審請求を受理しました」を約1秒出して④へ
- `prefers-reduced-motion: reduce` の人には③を出さず、すぐ④へ
- 判定とカードの描画は③に入った時点で始め、待ち時間とは関係なく終わらせておく

### ④ 交付
- カードが裏から表にめくれる（今の演出のまま）。SSR・SR はキラキラが流れる（今のまま）
- カードの下に「第一審」または「再審 N 回目」と「判定：〇〇」
- ボタン：「異議を申し立てる」（③の再審版を経て④へ）・「画像を保存」（今の仕組みのまま。直すのは D）・「別の持ち物を鑑定する」（入力と写真を空にして②へ）
- 広告枠、その下に「同じ系統の神器」（アフィリエイト）の枠
- 判定の決まり（乱数の種・再審回数のリセット条件など）は今と同じ

## 7. ほかの3ページ

4ページともヘッダー・フッター・色・書体は共通（`site.css`）。中身は文章が中心で、申請書と同じ生成りの紙の上に載せる。

### 鑑定所について（about.html）
- 鑑定所の設定（神様の役所で、持ち物を神器として鑑定する窓口）
- 「架空の団体で、実在の宗教・団体とは関係ありません」
- 鑑定の決まり：判定は写真・名前・種類で決まり、同じなら同じ結果。異議を申し立てると再審
- ランクの出やすさ（SSR 3%・SR 10%・R 25%・N 40%・Z 22%）とステータス4つの見方
- 写真の扱い：端末の中でカードに合成するだけで、送らない・保存しない

### プライバシーポリシー・免責事項（privacy.html）
- 写真・入力した名前は外に送らないこと
- 広告について：今は広告を入れていないので「今後、広告配信（Google AdSense 等）を利用する予定で、その際は Cookie を使うことがある」と書く。広告を入れる D の段階で、最新の掲載要件を確認して書き直す
- 判定は娯楽で、ご利益などの効果はないという免責
- 制定日を書く
- 文案は Claude が作り、公開前に運営者が確認する

### お問い合わせ（contact.html）
- 匿名運営なので、メールアドレスを出さない Google フォームへのリンクにする
- フォームは運営者が作る。リンク先が決まるまでは「お問い合わせ窓口は準備中です」と表示する

## 8. エラーの扱い

| 場面 | 表示 |
|---|---|
| 品名が空のまま「申請する」 | 品名の欄の下に「品名をご記入ください。」と出し、品名の欄にフォーカスを移す |
| 写真がないまま「申請する」 | 写真の欄の下に「現物写真を添付してください。」と出し、「写真を添付する」ボタンにフォーカスを移す |
| 写真が読み込めない（対応していない形式・壊れたファイル） | 写真の欄の下に「この写真は読み込めませんでした。別の写真をお試しください。」 |
| Google Fonts が読み込めない | 端末の明朝体・ゴシック体で表示する（今と同じ） |

案内は各欄に `aria-describedby` で結び付ける。フォーカスがその欄に移るので、画面読み上げでも欄の名前と一緒に案内が読まれる。

## 11. テスト

### 判定のテスト（Vitest）
- ファイルを分ける**前に**、今の `shinki-kantei.html` から判定に関わる部分（`hash`・`rng`・単語の表・`appraise`）を取り出し、数十通り（名前・種類7つ・写真の署名・再審回数 0〜2 の組み合わせ）の結果を JSON に記録する
- 分けたあとの `appraise.js` が、同じ入力に対して記録と完全に一致することを確かめる
- この記録は今回の作り直しで判定が変わらないことを守るためのもの。A で部品を増やすと結果は意図して変わるので、そのときに記録を作り直す

### 画面のテスト（Playwright、パソコン幅とスマホ幅）
今の `tests/smoke.spec.js` を置き換える。ビルドしたもの（`http://web/`）に対して流す。
- ①で「番号札を取る」→②へ進み、受付番号が出る
- ②で見本の写真を使い「申請する」→③→④でカード（750×1050）が出る
- ③はタップで飛ばせる
- 動きを減らす設定では③を出さずに④になる
- 「異議を申し立てる」で再審の回数が増える
- 品名・写真が空のときに、それぞれの欄の下に案内が出る
- ブラウザの「戻る」で1つ前の画面に戻る
- 同じ写真・名前・種類なら、開き直しても同じ判定になる
- 3ページが開き、ヘッダーとフッターが出る
- 横スクロールが出ない

## 12. A（言葉の部品を増やす）に引き継ぐこと

- ③の審査の文言は、今回は数個だけ用意する。A で由来・効果・弱点と一緒に増やす
- 文言に「懐かしネタ」を入れる（2026年10月5日に運営者と決定）
  - 時代は昭和（1970〜80年代）と平成（1990〜2000年代）をまんべんなく混ぜる
  - ターゲット層がまだ決まっていないので、懐かしネタの部品には時代の印（昭和・平成）を付け、あとから出やすさの比率を変えられるようにする
  - 商品名・キャラクター名・曲の歌詞・作品の決めぜりふは使わない（商標・著作権のため）。「黒電話」「ポケベル」「ブラウン管」「カセットテープ」のような一般的な名前と、あるあるの行動で懐かしさを出す
- ターゲット層をどう知るか（アクセス解析を入れるか、入れるなら何を使うか）は、プライバシーポリシーに関わるので D で決める
